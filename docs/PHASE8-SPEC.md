# SKYTOPIA: AETHER RISING
## DEVELOPMENT PHASE 8 — SKY RIVALS
### 하늘의 경쟁자들 — 온라인 경쟁, 협동 건설 및 글로벌 문명 네트워크

---

## 1. 프로젝트 개요

기존 SKYTOPIA: AETHER RISING 프로젝트를 기반으로 Phase 8 개발을 진행한다.

- 게임명: SKYTOPIA: AETHER RISING
- 장르: 3D 건설 퍼즐, 도시 운영, 구조 공학, 생존, 문명 전략, 온라인 경쟁
- 플랫폼: PC 웹 브라우저
- 기본 언어: 한국어
- 추가 지원 언어: 영어
- 그래픽 방향: 로우폴리 판타지와 미래 문명의 결합
- 플레이 방식: 싱글 플레이, 온라인 경쟁, 온라인 협동

### 기존 개발 단계

## 2. 이번 단계의 핵심 목표

**플레이어의 건축 능력, 구조 설계 능력, 도시 운영 능력 및 재난 대응 능력을 다른 플레이어와 비교하고 협력할 수 있는 온라인 게임을 구현한다.**

다음 핵심 기능을 개발한다.

- 온라인 게임 서버
- 플레이어 계정 또는 인증된 게스트
- 온라인 로비
- 게임 방 생성 및 참가
- 친구 초대
- 빠른 대전
- 동일 조건 경쟁
- 실시간 도시 상태 공유
- 온라인 점수 검증
- 구조 공학 경쟁
- 재난 생존 경쟁
- 문명 발전 경쟁

- 협동 문명 운영

최우선 목표는 서로 다른 두 브라우저에서 접속한 플레이어가 실제로 동일한 경기의 상태를 공유하며 플레이할 수 있는 것이다.

## 4. 온라인 개발 기본 원칙

SKYTOPIA의 온라인 시스템은 다음 원칙을 따른다.

### 공정성

같은 경쟁에서는 모든 플레이어가 동일한 초기 조건을 제공받는다.

### 서버 검증

클라이언트가 임의로 생성한 자원, 점수, 경기 결과를 그대로 신뢰하지 않는다.

### 싱글 플레이 보호

온라인 시스템과 오프라인 게임 상태를 분리한다.

### 접근성

처음 온라인 게임에 참여하는 사용자도 복잡한 설정 없이 게임 방에 입장할 수 있어야 한다.

### 안정성

일시적인 네트워크 문제로 진행 중인 경기가 즉시 소실되지 않도록 한다.

### 확장성

초기에는 2인 플레이를 안정적으로 구현하고 이후 4인 이상으로 확장할 수 있는 구조를 마련한다.

## 5. 기술 스택 및 서버 구성

기존 클라이언트 기술 스택을 유지한다.

### 클라이언트

- React
- TypeScript
- Vite
- Three.js
- React Three Fiber
- 기존 상태 관리 라이브러리

### 온라인 서버 권장 구성

- Node.js
- TypeScript
- Socket.IO 또는 검증된 WebSocket 기반 통신
- PostgreSQL 또는 호환되는 영구 데이터베이스
- 필요시 Redis

Redis는 초기 2인 멀티플레이 구현에 필수로 요구하지 않는다.

실제 서비스 규모가 증가할 때 매치메이킹, 세션 관리, 서버 간 상태 공유에 활용할 수 있도록 한다.

### 개발 환경

- 로컬 온라인 서버
- 로컬 데이터베이스 또는 개발용 저장 방식
- 두 개 이상의 브라우저로 테스트 가능
- 환경변수 기반 서버 주소 설정
- 개발 환경과 운영 환경 분리

기존 프런트엔드가 Vercel에 배포되어 있다면 이를 유지할 수 있다.

지속적인 WebSocket 연결과 권위 있는 게임 시뮬레이션이 필요한 서버는 장시간 실행되는 Node.js 프로세스를 지원하는 별도 서버 환경을 사용한다.

Vercel의 일반 서버리스 함수만으로 장시간 실행되는 멀티플레이 서버를 구성하려고 하지 않는다.

실제 운영 서버 계정이나 인증 정보가 준비되지 않은 경우 로컬 환경에서 완전한 온라인 테스트를 우선 구현하고 배포 방법을 문서화한다.

사용자 승인 없이 유료 서버를 생성하거나 결제하지 않는다.

## 6. 프로젝트 아키텍처

기존 구조를 분석하여 필요에 따라 모노레포 또는 독립 서버 구조를 적용한다.

권장 구조:

    apps/
      client/
      server/

    packages/
      shared/
      game-core/
      protocol/

기존 구조를 유지하는 편이 안전하다면 다음과 같은 방식도 허용한다.

    src/
      multiplayer/
        client/
        synchronization/
        prediction/
        rooms/
        matchmaking/
        replay/

    server/
      auth/
      rooms/
      matchmaking/
      simulation/
      validation/
      persistence/
      ranking/
      moderation/

    shared/
      gameRules/
      gameTypes/
      networkProtocol/
      validationSchemas/

게임의 핵심 계산 규칙은 가능한 범위에서 클라이언트와 서버가 공유하도록 구성한다.

동일한 구조 계산 공식이 클라이언트와 서버에서 서로 다르게 구현되어 결과가 불일치하는 문제를 방지한다.

서버 전용 권한과 비밀 정보는 클라이언트 번들에 포함하지 않는다.

## 7. 권위 있는 게임 서버

온라인 경쟁에서는 서버가 최종 게임 상태를 결정한다.

클라이언트는 플레이어의 입력과 행동 요청을 서버로 전송한다.

예시:

- 블록 이동
- 블록 회전
- 블록 배치
- 건축물 철거
- 구조 보강
- 시설 업그레이드
- 긴급 부양장치 사용
- 비행선 운항 요청
- 교역 설정

서버는 다음 조건을 검증한다.

- 현재 경기 상태
- 플레이어 권한
- 건축물의 유효성
- 현재 블록 ID
- 실제 보유 자원
- 격자 점유 상태
- 구조적 지지 여부
- 건축 가능 범위
- 기술 해금 여부
- 행동 횟수 제한
- 경기 종료 여부

유효한 행동만 게임 상태에 반영한다.

클라이언트가 직접 점수, 인구, 자원, 안정도 및 승리 결과를 결정하지 않도록 한다.

## 8. 온라인 시뮬레이션 동기화

기존 고정 시간 간격 시뮬레이션을 온라인 환경에 적용한다.

### 서버에서 관리할 상태

- 게임 시간
- 건축 블록 공급
- 난수 시드
- 도시 구조
- 자원
- 인구
- 경제
- 전력
- 식량
- 구조 하중
- 재난
- 경기 점수
- 승리 및 패배 조건

초기 권장값:

- 서버 시뮬레이션: 초당 5~10회
- 상태 갱신: 게임 특성에 맞추어 초당 2~10회
- 경제 계산: 기존 고정 시뮬레이션 기준 유지
- 클라이언트 렌더링: 독립적인 프레임 갱신

위 수치는 실제 네트워크 테스트를 통해 조정한다.

### 네트워크 최적화

전체 도시 데이터를 모든 프레임에 전송하지 않는다.

다음 방식을 활용한다.

- 초기 전체 상태 스냅샷
- 변경된 건축물 정보
- 자원 변화
- 구조 상태 변화
- 경기 이벤트
- 일정 간격의 검증용 스냅샷

건축물의 시각적 애니메이션은 클라이언트에서 처리하되 최종 게임 상태는 서버와 일치해야 한다.

## 9. 플레이어 입력 반응성

온라인 게임에서 네트워크 지연 때문에 블록 조작이 지나치게 느려지지 않도록 한다.

### 로컬 처리 가능 항목

- 카메라 회전
- 화면 확대 및 축소
- 층 선택
- 블록 배치 예상 모델
- 로컬 UI 조작
- 구조 분석 화면
- 일부 블록 이동 미리보기

### 서버 확인 필요 항목

- 최종 건축물 배치
- 자원 사용
- 블록 확정
- 구조물 철거
- 시설 업그레이드

서버가 배치를 거부하면 잘못된 예상 결과를 안전하게 원상 복구한다.

동일한 블록이 두 번 배치되는 문제와 자원이 중복 차감되는 문제를 방지한다.

## 10. 플레이어 계정 시스템

초기 온라인 플레이를 쉽게 시작할 수 있도록 한다.

### 게스트 플레이

- 임시 또는 영구적으로 식별 가능한 게스트 ID
- 플레이어 닉네임 설정
- 친선 경기 참가
- 비공개 게임 방 참가

게스트 ID는 서버가 발급한 세션 정보와 연결한다.

닉네임만으로 다른 플레이어의 계정에 접근할 수 없도록 한다.

### 정식 계정

운영 환경에서 사용할 인증 방식을 검토한다.

- 이메일 기반 인증
- OAuth 기반 계정 연결
- 기존 인증 서비스 활용

비밀번호 인증을 직접 구현할 경우 검증된 인증 라이브러리와 안전한 비밀번호 해싱을 사용한다.

초기에는 검증된 게스트 세션으로 실제 멀티플레이를 완성하고 정식 계정은 후속 우선순위로 진행할 수 있다.

정식 랭킹에는 지속적으로 식별 가능한 인증 계정을 사용한다.

- 온라인 랭킹
- 시즌 도전

실제로 작동하는 기능만 활성화한다.

온라인 서버 연결에 실패하면 다음 정보를 표시한다.

- 연결 상태
- 재연결 버튼
- 오류에 대한 간단한 설명
- 싱글 플레이로 돌아가기

온라인 연결 실패로 전체 게임 화면이 멈추지 않도록 한다.

## 13. 게임 방 생성

플레이어가 온라인 게임 방을 만들 수 있도록 한다.

### 방 설정

- 방 이름
- 공개 또는 비공개
- 경기 유형
- 최대 플레이어 수
- 경기 제한시간
- 초기 공중섬
- 난이도
- 건축 블록 공급 방식
- 재난 활성화 여부
- 재난 시드
- 관전자 허용 여부

초기 최대 플레이어 수는 2명으로 제한한다.

4인 이상 경기는 2인 시스템의 안정성이 검증된 이후 확장한다.

### 방 상태

- 대기 중
- 준비 완료
- 경기 시작 중
- 경기 진행 중
- 경기 종료
- 재경기 대기

방 생성과 경기 시작을 서버에서 관리한다.

## 14. 친구 초대 시스템

비공개 게임 방에는 고유한 초대 코드를 생성한다.

예시:

    SKY-8F4K2

다음 기능을 제공한다.

- 초대 코드 복사
- 초대 링크 복사
- 코드 입력 후 방 참가
- 참가자 닉네임 표시
- 준비 상태 표시
- 방장 권한 표시

초대 코드의 유효성 및 방 접근 권한을 서버에서 확인한다.

비공개 게임 방에 허가되지 않은 플레이어가 임의로 입장하지 못하도록 한다.

정식 친구 목록 시스템은 기본 초대 기능이 안정적으로 구현된 이후 추가할 수 있다.

## 15. 온라인 로비

게임 시작 전에 참가자가 함께 대기하는 화면을 구현한다.

표시 정보:

- 경기 모드
- 플레이어 프로필
- 경기 규칙
- 초기 공중섬
- 경기 제한시간
- 재난 설정
- 준비 상태
- 서버 연결 상태
- 네트워크 지연

모든 참가자가 준비 완료 상태가 되면 경기를 시작할 수 있다.

랭크 경기에서는 서버가 경기 조건을 결정한다.

친선 경기에서는 방장이 허용된 범위의 경기 조건을 변경할 수 있다.

게임 시작 직전에 플레이어가 준비 상태를 반복적으로 변경하여 경기 진행을 방해하는 문제를 최소화한다.

## 16. 매치메이킹 시스템

온라인 경쟁전을 위한 매치메이킹을 구현한다.

### 검색 조건

- 경기 유형
- 플레이어 랭크
- 네트워크 연결 상태
- 서버 지역
- 대기 시간

초기에는 간단한 대기열 기반 매칭을 사용한다.

플레이어 수가 적을 경우 검색 범위를 점진적으로 넓힌다.

### 매칭 진행

대전 검색
→ 상대방 발견
→ 경기 조건 확인
→ 참가 수락
→ 경기 로딩
→ 경기 시작

실제 상대방을 찾지 못했다고 가짜 온라인 플레이어를 생성하지 않는다.

AI 상대를 제공할 경우 AI 대전이라는 사실을 명확하게 표시한다.

매치메이킹 대기열을 취소할 수 있도록 한다.

## 17. 온라인 경기 공통 규칙

경쟁 경기에는 공정한 초기 조건을 적용한다.

### 동일 조건

- 동일한 초기 공중섬
- 동일한 초기 건축 자원
- 동일한 인구
- 동일한 기본 시설
- 동일한 부양력
- 동일한 기술 해금
- 동일한 블록 공급 규칙
- 동일한 경기 제한시간
- 동일한 재난 난수 시드

플레이어의 건축 선택에 따라 실제 도시의 발전 상태는 달라진다.

랭크 경쟁에서는 각 도시의 부족한 시설에 따라 블록 공급 확률을 개별적으로 보정하는 기존 싱글 플레이 규칙을 기본적으로 사용하지 않는다.

동일한 블록 공급 순서가 공정하게 유지되어야 한다.

각 플레이어는 자신만의 소비, 보관 및 재활용 선택에 따라 블록을 사용한다.

- 주요 전략적 차이

경기 종료 전 동일한 하중 시험을 적용할 수 있도록 한다.

시험 과정에서 구조물이 얼마나 안정적으로 유지되는지 평가한다.

단순히 기둥과 부양장치를 무한정 설치하는 것이 최적 전략이 되지 않도록 자원과 공간 제한을 적용한다.

- 사용한 블록 수

- 구조 안정성
- 완료 시간

건축 및 성장

- 재난 피해 최소화
- 주민 보호
- 핵심 시설 유지
- 도시 회복력
- 구조 복구
- 경제 회복

재난이 시작되기 전에 플레이어에게 충분한 대비 시간을 제공한다.

## 26. 협동 건축 충돌 처리

두 플레이어가 같은 위치에 동시에 건축물을 배치하는 상황을 처리한다.

### 규칙

- 서버가 배치 요청을 순서대로 검증한다.
- 먼저 유효하게 승인된 배치가 해당 공간을 차지한다.
- 이후 충돌하는 배치는 거부한다.
- 거부된 플레이어의 블록을 임의로 소멸시키지 않는다.
- 자원이 중복 차감되지 않도록 한다.

### 배치 예정 위치 공유

다른 플레이어가 현재 선택한 위치를 별도의 색상 또는 마커로 표시한다.

예시:

- 플레이어 A: 청록색
- 플레이어 B: 금색

다른 플레이어가 배치하려는 위치를 확인하여 충돌을 줄일 수 있도록 한다.

배치 예정 표시가 실제 점유 상태를 강제로 변경하지 않도록 한다.

## 27. 협동 자원 관리

협동 도시의 자원은 공유된다.

다음 기능을 제공한다.

- 현재 보유 자원
- 최근 자원 사용 기록
- 건축 예정 비용
- 비상 자원 비축
- 지출 권한
- 대규모 건축 확인

대규모 구조물 철거와 중요 시설의 제거는 추가 확인 절차를 적용할 수 있다.

다른 플레이어의 중요한 건축물을 악의적으로 제거하여 협동 플레이를 방해하는 행동을 방지한다.

### 보호 대상

- 핵심 에테르 코어
- 주요 발전시설
- 핵심 부양장치
- 필수 교통 연결
- 주요 구조 기둥

치명적인 영향을 주는 행동에는 공동 승인 또는 방장 권한을 적용할 수 있다.

일반적인 건축 행동에는 불필요한 승인 절차를 요구하지 않는다.

---

## 28. 협동 재난 대응

협동 플레이에서 자연재해가 발생하면 역할 분담을 활용할 수 있도록 한다.

예시:

공중 폭풍 접근.

플레이어 A:

- 구조 하중 분석
- 위험 기둥 보강
- 외곽 플랫폼 보호
- 부양력 관리

플레이어 B:

- 비상 전력 확보
- 주민 대피
- 식량 비축
- 산업시설 운영 조절

재난 종료 이후 양쪽 플레이어가 함께 복구를 진행한다.

두 플레이어가 협력할 때 혼자 운영하는 것보다 전략적 선택의 폭이 넓어지도록 한다.

협동 도시의 난이도는 두 명이 참여한다는 이유만으로 단순히 모든 피해량을 두 배로 증가시키지 않는다.

## 29. UNITED SKIES — 협동 문명 운영

각 플레이어가 서로 다른 공중 도시를 운영하며 하나의 문명을 완성하는 모드다.

### 플레이어 A

자신의 공중 도시를 건설하고 운영한다.

### 플레이어 B

다른 공중섬에 위치한 공중 도시를 건설하고 운영한다.

각 플레이어는 자신의 도시를 전문화할 수 있다.

예시:

- 농업 도시와 산업 도시
- 에너지 도시와 주거 도시
- 연구 도시와 교역 중심 도시

### 공통 목표

- 안정적인 도시 간 교역
- 공동 기술 연구
- 재난 지원
- 문명 전체 인구 증가
- 높은 문명 회복력
- 공동 최종 시설 건설

두 플레이어는 별도의 도시를 운영하지만 하나의 문명 목표를 공유한다.

## 30. 플레이어 간 자원 교역

Phase 7의 비행선 및 교역 시스템을 온라인 협동에 적용한다.

### 교역 방식

- 자원 제공
- 자원 요청
- 정기 자동 교역
- 긴급 물자 지원
- 상호 교환 계약

예시:

플레이어 A가 식량 100을 제공하고 플레이어 B가 건축 자원 60을 제공한다.

### 서버 검증

- 실제 보유 자원
- 교역 계약 승인
- 화물선 수용량
- 항구 상태
- 운송 가능 여부
- 실제 이동시간
- 자원 중복 이전 방지

온라인 자원도 실제 비행선을 통해 이동하도록 한다.

교역 요청만 생성했다고 자원이 즉시 복제되어 도착하지 않도록 한다.

거래 도중 연결이 끊어지더라도 이미 발생한 자원 이전과 화물 상태가 정확하게 유지되어야 한다.

자유 텍스트 채팅은 신고, 차단 및 스팸 제한 등 필요한 관리 기능과 함께 추가한다.

음성 채팅은 이번 단계의 필수 요구사항이 아니다.

## 34. 최종 경기 결과

### 결과 표시

- 경기 유형
- 승리한 플레이어
- 최종 점수
- 점수 차이
- 경기 시간
- 도시 인구
- 구조 안정성
- 경제 효율
- 재난 대응 성과
- 건축 효율
- 주요 경기 이벤트
- 랭크 변화
- 획득 경험치

두 플레이어의 도시를 결과 화면에서 비교할 수 있도록 한다.

### 동점 처리

다음 기준을 경기 모드에 맞추어 사전에 정의한다.

1. 필수 목표 달성 여부
2. 최종 종합 점수
3. 구조 안전성
4. 자원 및 건축 효율

모든 조건이 동일하면 무승부로 처리한다.

경기가 종료된 이후 새로운 건축 명령이나 자원 변경을 허용하지 않는다.

## 46. 경기 중 재접속

온라인 플레이 중 브라우저가 새로고침되거나 일시적으로 연결이 끊어지는 경우를 처리한다.

### 재접속 흐름

1. 연결 끊김 감지
2. 사용자에게 상태 표시
3. 서버 세션 유지
4. 자동 재연결 시도
5. 플레이어 권한 재확인
6. 현재 경기 상태 스냅샷 복원
7. 필요한 이후 이벤트 동기화
8. 정상 플레이 재개

초기 재접속 유예시간은 60~90초를 가안으로 설정한다.

경기 유형별로 연결 끊김 처리 정책을 다르게 적용할 수 있다.

### 랭크 경기

- 서버 경기 시간 계속 진행
- 개인 일시정지 불가
- 유예시간 내 재접속 허용
- 유예시간 초과 시 명확한 패배 처리 또는 경기 무효 조건 적용

### 친선 경기

방 설정에 따라 제한적인 전체 경기 일시정지를 허용할 수 있다.

### 협동 경기

남은 플레이어가 계속 도시를 운영하거나 공동 일시정지를 요청할 수 있다.

기존 싱글 플레이와 경쟁 플레이의 능력치를 분리할 수 있는 설정 구조를 마련한다.

경쟁 경기에서 특정 건축 전략만 지나치게 강력하지 않도록 검증한다.

### 검증 대상 전략

- 주거시설 집중 건설
- 산업시설 집중 건설
- 플랫폼만 대량 확장
- 부양장치 과도한 설치
- 경제 활동 최소화
- 재난 방어시설 집중
- 자원 비축만 수행
- 고층 도시 집중 건설
- 낮고 넓은 도시 건설

어떠한 한 가지 전략이 모든 상황에서 압도적인 우위를 갖지 않도록 한다.

실제 경기 기록과 테스트 결과를 기반으로 수치를 조정한다.

경기 규칙과 밸런스 데이터에 버전을 부여하여 리플레이와 랭킹 기록을 보호한다.

## 63. 운영 환경 및 배포

기존 프런트엔드 배포 환경을 우선 유지한다.

온라인 게임 서버는 WebSocket 연결과 지속적인 시뮬레이션을 지원하는 실행 환경에 배포할 수 있도록 준비한다.

### 배포 구성

- 프런트엔드 웹 애플리케이션
- 온라인 게임 서버
- 데이터베이스
- 인증 시스템
- HTTPS 및 WSS
- 환경변수
- 서버 상태 확인 엔드포인트
- 오류 로그
- 백업 및 복구 정책

### 환경변수 예시

    VITE_MULTIPLAYER_URL
    DATABASE_URL
    SESSION_SECRET
    ALLOWED_ORIGINS
    NODE_ENV

실제 비밀키를 저장소에 커밋하지 않는다.

.env.example에는 변수 이름과 설명만 작성한다.

서버 호스팅 정보가 준비되지 않은 경우 로컬에서 실행 가능한 서버를 완성한다.

README.md에 서버 배포를 위해 사용자가 직접 진행해야 할 단계를 작성한다.

실제로 외부 인터넷에서 접속을 검증하지 않았다면 공개 온라인 서비스가 완성되었다고 보고하지 않는다.

## 73. Phase 8 핵심 완료 기준

다음 과정이 두 개 이상의 실제 브라우저에서 작동해야 한다.

플레이어 A 접속
→ 게임 방 생성
→ 초대 코드 발급
→ 플레이어 B 접속
→ 게임 방 참가
→ 준비 완료
→ 동일한 조건에서 경기 시작
→ 무작위 건축 블록 공급
→ 각 플레이어 도시 건설
→ 실제 서버 검증
→ 도시 상태 동기화
→ 경기 점수 갱신
→ 경기 종료
→ 승리 및 패배 판정
→ 경기 결과 확인

협동 플레이에서는 다음 과정이 작동해야 한다.

두 플레이어 참가
→ 공유 공중 도시 생성
→ 역할 분담
→ 동시 건축
→ 공유 자원 사용
→ 구조 보강
→ 공동 목표 달성
→ 협동 경기 완료

온라인 서버 연결 없이 기존 싱글 플레이도 정상적으로 실행되어야 한다.
